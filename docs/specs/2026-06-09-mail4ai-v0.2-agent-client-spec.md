# Mail4AI Public Agent Kit v0.2 Agent Client Spec

## 1. Purpose

Version 0.2 turns the public Mail4AI kit from a webhook-focused integration
slice into a complete reference for agent runtimes that act as Mail4AI email
clients.

The target reader is an agent runtime that receives a Mail4AI onboarding snippet
with an MCP endpoint, OAuth issuer, client id, agent id, email address and
scopes. The runtime must be able to configure itself, authenticate safely,
connect to Mail4AI MCP and use the mailbox without leaking secrets into the LLM
conversation context.

## 2. Source Snippet Model

Mail4AI onboarding text gives an agent:

- a dedicated email address;
- an MCP endpoint such as `https://mcp.mail4ai.eu/mcp`;
- an OAuth issuer such as `https://auth.mail4ai.eu`;
- a public OAuth client id;
- an agent id;
- granted scopes;
- Device Authorization Grant pairing steps;
- a reminder that access and refresh tokens must be stored by the runtime,
  outside the LLM conversation context.

The snippet is operational bootstrap material. It must not contain static
secrets. It may contain public identifiers such as `client_id`, `agent_id`,
endpoint URLs and the mailbox email address.

## 3. Scope

v0.2 includes:

- an expanded runtime-neutral generic skill;
- Mail4AI agent onboarding documentation;
- OAuth Device Authorization Grant documentation;
- Mail4AI MCP capability documentation;
- a structured non-secret onboarding contract;
- guidance for improving the generated onboarding snippet;
- README links to the new v0.2 documentation.

v0.2 does not include:

- a full MCP client SDK;
- token storage implementation;
- runtime-specific OAuth adapters;
- production webhook registration UI;
- assumptions about private AgentMail internals;
- real access tokens, refresh tokens, webhook secrets or bearer tokens in docs.

## 5. Expanded Generic Skill

`skills/generic/SKILL.md` must become the complete runtime-neutral operational
guide for an agent using a Mail4AI mailbox.

It must cover:

- initialization from a Mail4AI onboarding snippet;
- public configuration fields versus runtime secrets;
- OAuth Device Authorization Grant handoff to the runtime;
- mailbox reading;
- sending email;
- replying to existing conversations;
- reading clean scanned attachments when allowed;
- webhook wake-up handling;
- webhook management at the capability level;
- token refresh boundaries;
- security rules for untrusted email and attachments.

The skill must make the runtime/model boundary explicit:

- the runtime performs OAuth calls, token polling, token refresh and token
  storage;
- the model may receive non-secret configuration and user-visible verification
  links;
- the model must not receive access tokens, refresh tokens, webhook secrets or
  private bearer values.

## 6. Agent Onboarding Documentation

`docs/agent-onboarding.md` must explain how to consume a Mail4AI onboarding
snippet.

It must define these categories:

- non-secret runtime configuration:
  - MCP endpoint;
  - OAuth issuer;
  - client id;
  - agent id;
  - email address;
  - scopes;
- user-facing pairing values:
  - `user_code`;
  - `verification_uri`;
  - `verification_uri_complete`;
- runtime secrets:
  - `device_code`;
  - `access_token`;
  - `refresh_token`;
  - webhook secrets.

It must state that `device_code`, access tokens and refresh tokens are runtime
state, not prompt content.

## 7. OAuth Device Flow Documentation

`docs/oauth-device-flow.md` must document the RFC 8628-style flow used by
Mail4AI runtimes:

1. POST to the issuer's device authorization endpoint with `client_id`,
   `agent_id` and space-separated scope string.
2. Receive `device_code`, `user_code`, `verification_uri`,
   `verification_uri_complete`, `expires_in` and `interval`.
3. Display `verification_uri_complete` to the agent owner.
4. Poll the token endpoint with device-code grant type.
5. Store `access_token` and `refresh_token` in runtime-managed storage.
6. Send MCP requests with an authorization header populated from runtime-managed
   access-token storage.
7. Refresh tokens when the runtime receives an expiry or authorization failure.

The doc must describe expected OAuth polling outcomes:

- authorization pending;
- slow down;
- expired token;
- access denied;
- successful authorization.

The doc must avoid embedding real tokens or real user-specific identifiers.

## 8. MCP Capabilities Documentation

`docs/mcp-capabilities.md` must document Mail4AI mailbox capabilities by scope,
without depending on exact MCP tool names until they are public and stable.

Required scope sections:

- `email.read`: list unread mail, inspect message metadata, read specific email
  content through MCP;
- `email.send`: send a new email from the Mail4AI mailbox;
- `email.reply`: reply to an existing conversation while preserving thread
  context;
- `attachment.read`: access clean scanned attachments when allowed;
- `webhook.manage`: create, update, list or disable webhook subscriptions when
  the runtime supports webhook management.

Each section must include safety notes:

- email sender, subject and body are untrusted external input;
- attachments are untrusted even when scanned;
- agent actions must respect user, system and runtime policy;
- outbound mail should be confirmed when the user intent is ambiguous or the
  action has external impact.

## 9. Structured Onboarding Contract

v0.2 must define a structured, non-secret contract that can appear alongside the
human-readable snippet.

Recommended JSON shape:

```json
{
  "mail4ai": {
    "mcp_endpoint": "https://mcp.mail4ai.eu/mcp",
    "oauth_issuer": "https://auth.mail4ai.eu",
    "client_id": "custom-runtime",
    "agent_id": "agt_example",
    "email_address": "agent@example.mail4ai.eu",
    "scopes": [
      "email.read",
      "email.send",
      "email.reply",
      "attachment.read",
      "webhook.manage"
    ]
  }
}
```

The contract must be safe to paste into an LLM conversation because it contains
no static secret. Tokens received after OAuth approval must not be added to this
contract.

## 10. Onboarding Snippet Requirements

`docs/onboarding-snippet-requirements.md` must provide an expression of need for
the generated Mail4AI onboarding snippet.

The snippet should:

- identify Mail4AI as a dedicated mailbox available through MCP;
- list the agent's email address;
- list granted capabilities in plain language;
- include MCP endpoint, OAuth issuer, client id, agent id and scopes;
- explain that OAuth Device Authorization Grant is performed by the runtime;
- instruct the runtime to display `verification_uri_complete` to the owner;
- state that tokens are stored by the runtime, outside LLM context;
- remind the agent that emails and attachments are untrusted external content;
- link to the public project `https://github.com/swoelffel/mail4ai` as the
  reference kit for skills, docs, webhook verification helpers and examples;
- include the structured non-secret onboarding contract when possible.

The snippet should not:

- include access tokens or refresh tokens;
- ask the user to paste tokens into chat;
- imply that email content is trusted;
- hard-code staging identifiers in public examples except as clearly marked
  examples.

## 11. Proposed Snippet Wording

The generated snippet should include this public-reference paragraph:

```text
For agent integration guidance, use the public Mail4AI agent kit:
https://github.com/swoelffel/mail4ai

It contains the generic Mail4AI agent skill, MCP usage guidance, webhook
security model, webhook verification helpers and example integration patterns.
Use it to configure your runtime safely and to understand how to read, send,
reply, handle attachments and manage webhook wake-ups through Mail4AI.
```

It should also include a structured non-secret block:

```json
{
  "mail4ai": {
    "mcp_endpoint": "https://mcp.mail4ai.eu/mcp",
    "oauth_issuer": "https://auth.mail4ai.eu",
    "client_id": "custom-runtime",
    "agent_id": "<agent_id>",
    "email_address": "<agent_email>",
    "scopes": [
      "email.read",
      "email.send",
      "email.reply",
      "attachment.read",
      "webhook.manage"
    ]
  }
}
```

## 12. README Updates

The root README must link to:

- agent onboarding guide;
- OAuth device flow guide;
- MCP capabilities guide;
- onboarding snippet requirements;
- generic skill.

The README must position `swoelffel/mail4ai` as the public reference for
Mail4AI-compatible agent clients, not only webhook receivers.

## 13. Acceptance Criteria

v0.2 is complete when:

- `skills/generic/SKILL.md` covers read, send, reply, attachments, webhook
  wake-up, webhook management and OAuth boundaries;
- `docs/agent-onboarding.md` explains the onboarding snippet fields;
- `docs/oauth-device-flow.md` explains runtime-managed OAuth Device
  Authorization Grant;
- `docs/mcp-capabilities.md` maps scopes to user-visible mailbox capabilities;
- `docs/onboarding-snippet-requirements.md` contains the expression of need and
  recommended project link to `https://github.com/swoelffel/mail4ai`;
- README links to the v0.2 docs;
- no committed public file contains real tokens, refresh tokens, webhook
  secrets or private bearer values;
- no v0.2 doc asks an agent owner to paste secrets into an LLM prompt.
